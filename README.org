Submission for WebClub (Systems & Security) & IRIS.

* Task

The chosen task is "Operating Systems".

** Introduction

The task involves the following goals:

- Secure boot in user mode
- Encrypt a disk in-place using ~cryptsetup reencrypt~
- Fix the boot process to ask for luks passphrase
- Set up a MOK
- TPM 2.0 unlocking with relevant PCRs

This document covers all 5 expected steps in the original task document.

All the relevant configurations are tangled using ~org-babel~ from this document.

*** Notation for command blocks

Command blocks starting with ~$~ are to be ran on the host.

Command blocks starting with ~%~ are to be ran as user ~foo~ on the foobar vm.

Command blocks starting with ~#~ are to be ran as user ~root~ on the foobar vm.

** Operating System - foobar

The original problem involved using Ubuntu. This solution uses my own project, [[https://github.com/sotormd/foo][foobar]], which is a minimal LFS-like
system provisioned using the [[https://github.com/nixos/nix][Nix]] package manager and the [[https://github.com/nixos/nixpkgs][Nixpkgs]] package repository. Secureboot support was added to
foobar in [[https://github.com/sotormd/foo/pull/1][foo#1]] specifically for this challenge.

Since foobar eliminates all distribution-specific differences, implementing a solution like this
requires very explicit steps along the way.

Differences between Ubuntu and foobar:

- foobar does not use systemd, it does not use a service manager at all
- foobar is provisioned using Nix, which guarantees reproducibility
- foobar has no real "defaults" and everything is largely up to the user
- for all practical purposes, foobar just describes the commands that should run
  in initrd and init (PID 1), everything else is a subsequent consequence

Differences between LFS (book) and foobar:

- minimal compiling, using Nix substituters
- no PAM, no dbus, no systemd/sysvinit, no unnecessary complexity

Differences between vanilla NixOS and foobar:

- no NixOS module system, foobar is extensible using
  fixed-point combinators
- no layer of abstraction over simple shell scripts
- many NixOS concepts (activation, generations, nixos-rebuild)
  have semi-equivalent implementations for foobar
- ~/etc~ is an EROFS image instead of a symlink farm

It is *highly* recommended to read the [[https://github.com/sotormd/foo/blob/master/README.md][foo & foobar README]] before reading the rest of this submission.

Before we proceed, we should fetch foobar so we can extend it:

#+BEGIN_SRC nix :tangle foobar.nix
  let
    commit = "4c0f66dae627ab6ca48278141ec0c9893b526814";
    hash = "sha256-KiRy+yLyhPIN9yJXWsa/vhKHAFmt4hgner2PBnECFkA=";

    foo = fetchTarball {
      url = "https://github.com/sotormd/foo/archive/${commit}.tar.gz";
      sha256 = hash;
    };

    configuration = import "${foo}/foobar/configuration.nix";
    
    finalConfiguration = configuration.extend (
      final: prev: let
        configs = final.pkgs.runCommand "configs" { } ''
          mkdir -p $out
          cp ${./foobar.nix} $out/foobar.nix
          cp ${./config-1-install.nix} $out/config-1-install.nix
          cp ${./config-2-secureboot.nix} $out/config-2-secureboot.nix
          cp ${./config-3-initrd-shell.nix} $out/config-3-initrd-shell.nix
          cp ${./config-4-luks.nix} $out/config-4-luks.nix
          cp ${./config-5-tpm.nix} $out/config-5-tpm.nix
        '';
      in
      {
        activateCommands = builtins.concatStringsSep "\n" [
          prev.activateCommands
          ''
          echo activate: linking configs

          ln -sfn ${configs} /run/configs
          ''
        ];
      }
    );
  in
  finalConfiguration
#+END_SRC

The above expression is tangled to [[foobar.nix][foobar.nix]]. this can be used for all subsequent extensions.

Note that we also add a activation hook that links all configs to ~/run/configs~ so that we can
switch to future generations without cloning this repository.

** Step 1: Installing

This section covers installing and preparing the foobar system.

*** Building disk image

foobar provides a ~diskImage~ output which, by default, creates a fat32 ~/boot~ with the foobar UKI and bootloader,
and a xfs rootfs. This is ideal for this problem, since we want to start with an unencrypted rootfs and work
towards reencrypting it (foreshadowing: it is not ideal).

The first thing we need to do is to create a foobar "configuration", which exploits the fact that the upstream foobar
configuration is extensible using fixed-point combinators. Note that for the first install, we do not need to change
anything about the default configuration. The configuration will look like this:

#+BEGIN_SRC nix :tangle config-1-install.nix
  let
    configuration = import ./foobar.nix;
  in
  configuration.foo
#+END_SRC

The above expression is tangled to [[config-1-install.nix][config-1-install.nix]].

#+BEGIN_SRC console
  $ git clone https://github.com/sotormd/wc && cd wc
  $ nix build -f config-1-install.nix build.diskImage
  $ cp result image.raw
  $ chmod +w image.raw
#+END_SRC

This gives us a ~image.raw~ that we can work with.

*** First boot

The generated image can be booted using QEMU. Since we want secureboot support we need ~OVMF_CODE.secboot.fd~
and ~OVMF_VARS.secboot.fd~. I used the ones from Fedora's koji builds, they are included in this repository
under [[assets][assets]].

Unlike Ubuntu, foobar does not (and cannot) use Microsoft's secureboot shim. This means that the only way to
use secureboot is to enroll our own PK, KEK, and db certs. So, we have to disable secureboot for the first boot.
To disable secure boot, reboot into the firmware interface and uncheck ~Attempt Secure Boot~.

For first boot :-

#+BEGIN_SRC console
  $ cp assets/* .
  $ qemu-system-x86_64 \
    -machine q35,smm=on,accel=kvm \
    -m 16G \
    -smp 6 \
    -global driver=cfi.pflash01,property=secure,value=on \
    -drive if=pflash,format=raw,unit=0,file="OVMF_CODE.secboot.fd",readonly=on \
    -drive if=pflash,format=raw,unit=1,file="OVMF_VARS.secboot.fd" \
    -device ahci,id=ahci \
    -drive id=disk,file="image.raw",format=raw,if=none \
    -device ide-hd,drive=disk,bus=ahci.0 \
    -netdev user,id=net0 \
    -device virtio-net-pci,netdev=net0 \
    -nographic
#+END_SRC

*** Secure Boot

As mentioned earlier, unlike Ubuntu, foobar does not use the Microsoft secureboot shim. This means that we need
to sign the UKI & bootloader for each generation ourselves. Luckily, as of last week, foobar already has decent
secureboot support ootb.

In order to enroll our own keys, we must boot in Setup Mode. With the QEMU OVMF firmware, this can be done by
deleting any existing Platform Key(s). Reboot into the firmware interface and click ~Reset all Secure Boot keys~.
Next time we boot, we will be in Setup Mode.

Once booted, we can use the new ~foobar-generate-secureboot-keys~ and ~foobar-enroll-secureboot-keys~,
which use ~sbctl~ to create and enroll a PK, KEK and signing db key and cert.

#+BEGIN_SRC console
  # foobar-generate-secureboot-keys
  # foobar-enroll-secureboot-keys
#+END_SRC

At this stage, we have enrolled the keys but our UKI & bootloader are unsigned. We will use ~foobar-rebuild~ to
rebuild a new generation with ~secureBootEnabled~ set to true.

#+BEGIN_SRC nix :tangle config-2-secureboot.nix
  let
    configuration = import ./foobar.nix;

    finalConfiguration = configuration.extend (
      _: _: { secureBootEnabled = true; }
    );
  in
  finalConfiguration.foo
#+END_SRC

The above expression is tangled to [[config-2-secureboot.nix][config-2-secureboot.nix]].

#+BEGIN_SRC console
  # export FOOBAR_CONFIG=/run/configs/config-2-secureboot.nix
  # foobar-rebuild boot
#+END_SRC

Reboot and notice that the firmware prevents booting into generation 1. Only generation 2 works since it uses a signed UKI.

At this stage, for all practical purposes, we are on-par with a default Ubuntu installation.

** Step 2: Encrypt the root partition in place

On Ubuntu, this would usually be done using a live ISO. Since foobar uses the NixOS-like concept of "generations" we simply need
a generation where the real root is never mounted. This can be done by either:

- mounting a real system as tmpfs or
- never leaving initrd

For this task, we will create a generation that never leaves initrd.

#+BEGIN_SRC nix :tangle config-3-initrd-shell.nix
  let
    configuration = import ./foobar.nix;

    finalConfiguration = configuration.extend (
      final: prev:
      {
        secureBootEnabled = true;
        
        initrdModules = prev.initrdModules ++ [
          "dm_mod"
          "cbc"
          "xts"
          "encrypted_keys"
          "trusted"
          "dm_crypt"
        ];

        initrdPackages = prev.initrdPackages ++ [
          final.pkgs.cryptsetup
          final.pkgs.bashInteractive
        ];

        initrdCommands = ''
          mkdir -p /proc /sys /dev
          mount -t proc proc /proc
          mount -t sysfs sysfs /sys
          mount -t devtmpfs devtmpfs /dev

          ${final.loadModules final.initrdModules}

          exec bash # leaving will cause a kernel
                    # panic but thats alright :p
        '';
      }
    );
  in
  finalConfiguration.foo
#+END_SRC

The above expression is tangled to [[config-3-initrd-shell.nix][config-3-initrd-shell.nix]].

The exact order of the modules are also important, loading them in any other order will lead to unknown symbol
errors and the ~cryptsetup luksOpen~ will fail.

#+BEGIN_SRC console
  # export FOOBAR_CONFIG=/run/configs/config-3-initrd-shell.nix
  # foobar-rebuild boot
#+END_SRC

Now, booting into generation 3 will drop into a bash shell with all the required tools to encrypt the disk in-place.

Once booted into the initrd shell, we can cryptsetup reencrypt the disk. BUT there is a catch, something I had completely
ignored while building the default ~diskImage~: XFS filesystems cannot be shrunk, at all. This matters because when we
~cryptsetup reencrypt~ a block device, we require space for a luks header. The two choices we have now are:

- scrap everything and use ext4 or
- since this is a virtual disk, use ~qemu-img~ to increase the size

We will increase the disk and partition size from the host without increasing the XFS filesystem size. On a real disk,
the solution is to provision the XFS filesystem while leaving some space.

#+BEGIN_SRC console
  $ qemu-img resize image.raw +128M
  $ sgdisk -e image.raw
  $ parted -s image.raw "resizepart 2 100%"
#+END_SRC

Now we can boot into generation 3, which drops us into an initrd shell.

#+BEGIN_SRC console
  # cryptsetup reencrypt --encrypt --reduce-device-size 32M /dev/sda2
  # cryptsetup isLuks /dev/sda2
  # echo $?  # -> returns 0 because it is a luks device
  # cryptsetup luksOpen /dev/sda2 drive
  # mkdir -p /mnt
  # mount -t xfs /dev/mapper/drive /mnt
  # ls /mnt
  nix home var
  # umount /mnt
#+END_SRC

At this stage we have encrypted an XFS disk in-place using ~cryptsetup reencrypt~. Now we can boot into the system from
the initrd itself, and later create a generation 4 that does it automatically as part of the boot process.

For now, we need to mount and ~switch_root~ manually. Mount the partitions as foobar usually does.

First, a tmpfs root:

#+BEGIN_SRC console
  # mkdir -p /root
  # mount -t tmpfs tmpfs /root
#+END_SRC

Then, the persistent disk:

#+BEGIN_SRC console
  # mkdir -p /root/persist
  # mount -t xfs /dev/mapper/drive /root/persist
#+END_SRC

Then, the boot partition:

#+BEGIN_SRC console
  # mkdir -p /root/boot
  # mount -t vfat /dev/sda1 /root/boot
#+END_SRC

Then, the Nix store:

#+BEGIN_SRC console
  # mkdir -p /root/nix
  # mount -o bind /root/persist/nix /root/nix
  # mount -o bind /root/nix/store /root/nix/store
  # mount -o remount,ro,bind,nosuid,nodev /root/nix/store
#+END_SRC

Then, the user homes:

#+BEGIN_SRC console
  # mkdir -p /root/home
  # mount -o bind,nosuid,nodev /root/persist/home /root/home
#+END_SRC

Similarly, var:

#+BEGIN_SRC console
  # mkdir -p /root/var
  # mount -o bind,nosuid,nodev /root/persist/var /root/var
#+END_SRC

The tree under ~/root~ is now identical to what the foobar initrd constructs, we can ~switch_root~ safely.

#+BEGIN_SRC console
  # exec switch_root /root "$BOOTED_CLOSURE/init"
#+END_SRC

** Step 3: Fix the boot process

After init, we should arrive at the login prompt as usual. Log in as root and switch to a generation that will
unlock the luks device automatically.

#+BEGIN_SRC nix :tangle config-4-luks.nix
  let
    configuration = import ./foobar.nix;

    finalConfiguration = configuration.extend (
      final: prev:
      {
        secureBootEnabled = true;
        
        initrdModules = prev.initrdModules ++ [
          "dm_mod"
          "cbc"
          "xts"
          "encrypted_keys"
          "trusted"
          "dm_crypt"
         ];

        initrdPackages = prev.initrdPackages ++ [
          final.pkgs.cryptsetup
        ];

        initrdFindRealRootCommands = ''
          boot=/dev/sda1
          cryptroot=/dev/sda2
          root=/dev/mapper/drive
          cryptsetup luksOpen "$cryptroot" drive
        '';
      }
    );
  in
  finalConfiguration.foo
#+END_SRC

The above expression is tangled to [[config-4-luks.nix][config-4-luks.nix]].

Note that on a real system, we should use PARTUUIDs instead of identifiers like sda1, sda2.

#+BEGIN_SRC console
  # export FOOBAR_CONFIG=/run/configs/config-4-luks.nix
  # foobar-rebuild boot
#+END_SRC

Booting into generation 4 should prompt for a password during initrd and arrive at a usable system
as expected.

** Step 4: Set up MOK

We don't need to do this, we can already sign any arbitrary artifact. In fact, our UKI and bootloader
is currently self-signed using ~sbsigntool~ as part of ~foobar-rebuild~.

Setting up MOK makes sense if you use Microsoft's shim. We don't do that here, this is largely a non-issue.

** Step 5: Set up automatic unlocking with TPM 2.0

We need to pass a swtpm device to QEMU, the new QEMU command becomes:

#+BEGIN_SRC console
  $ mkdir tpm
  $ swtpm socket -d --tpmstate dir="tpm" \
     --ctrl type=unixio,path="tpm/swtpm-sock" \
     --tpm2 \
     --log level=20
#+END_SRC

#+BEGIN_SRC console
  $ qemu-system-x86_64 \
     -machine q35,smm=on,accel=kvm \
     -m 16G \
     -smp 6 \
     -global driver=cfi.pflash01,property=secure,value=on \
     -drive if=pflash,format=raw,unit=0,file="OVMF_CODE.secboot.fd",readonly=on \
     -drive if=pflash,format=raw,unit=1,file="OVMF_VARS.secboot.fd" \
     -device ahci,id=ahci \
     -drive id=disk,file="image.raw",format=raw,if=none \
     -device ide-hd,drive=disk,bus=ahci.0 \
     -netdev user,id=net0 \
     -device virtio-net-pci,netdev=net0 \
     -nographic \
     -chardev socket,id=chrtpm,path="tpm/swtpm-sock" \
     -tpmdev emulator,id=tpm0,chardev=chrtpm \
     -device tpm-tis,tpmdev=tpm0
#+END_SRC

Boot into generation 4 (it asks for luks password) and you should be able to see a ~/dev/tpm0~.

#+BEGIN_SRC console
  # ls /dev/tpm0
  # nix shell github:nixos/nixpkgs#tpm2-tools
  # export TPM2TOOLS_TCTI="device:/dev/tpm0"
  # tpm2_getcap properties-fixed
  TPM2_PT_FAMILY_INDICATOR:
    raw: 0x322E3000
    value: "2.0"
  ...
  # tpm2_pcrread sha256:7
  sha256:
    7 : 0xFCF71D46154B9CFB59F2B306370D6C42E442475644503E16D22FC5E301A6B87B
  # exit
#+END_SRC

Now that we have TPM 2.0 working, we can use ~clevis~ to enroll the luks key in the TPM device.

#+BEGIN_SRC console
  # nix shell github:nixos/nixpkgs#clevis
  # clevis luks bind -d /dev/sda2 tpm2 '{"pcr_ids":"7"}'
  Enter existing LUKS password: 
  # clevis luks list -d /dev/sda2
  1: tpm2 '{"hash":"sha256","key":"ecc","pcr_bank":"sha1","pcr_ids":"7"}'
  # exit 
#+END_SRC

PCR 7 is secureboot state, so the TPM releases the key only if the secureboot state is as expected.
For example, disabling secureboot will result in the TPM not releasing the key.

The final configuration will have to attempt automatic unlocking in initrd.

#+BEGIN_SRC nix :tangle config-5-tpm.nix
  let
    configuration = import ./foobar.nix;

    finalConfiguration = configuration.extend (
      final: prev:
      {
        secureBootEnabled = true;

        initrdModules = prev.initrdModules ++ [
          "dm_mod"
          "cbc"
          "xts"
          "encrypted_keys"
          "trusted"
          "dm_crypt"
        ];

        # packages and lib for clevis is based on
        # non-systemd initrd configuration from
        # https://github.com/nixos/nixpkgs/blob/nixos-unstable/nixos/modules/system/boot/clevis.nix
        # because it is super convoluting and requires so many seemingly-unrelated things ;-;

        initrdPackages = prev.initrdPackages ++ [
          final.pkgs.cryptsetup
          final.pkgs.clevis

          # for clevis' shebang
          (builtins.dirOf (builtins.dirOf final.pkgs.runtimeShell))

          # used by clevis
          final.pkgs.tpm2-tools
          final.pkgs.tpm2-tss
          final.pkgs.jose
          (final.lib.hiPrio final.pkgs.coreutils) # hiPrio because more imp than busybox
          (final.lib.hiPrio final.pkgs.gnugrep)
          (final.lib.hiPrio final.pkgs.gnused)
        ];

        # required for tpm2_pcrread and stuff
        initrdContents = prev.initrdContents ++ [
          {
            source = "${final.pkgs.tpm2-tss}/lib/libtss2-tcti-device.so.0";
            target = "/lib/libtss2-tcti-device.so.0";
          }
        ];

        initrdFindRealRootCommands = ''
          boot=/dev/sda1
          cryptroot=/dev/sda2
          root=/dev/mapper/drive

          if ! clevis luks unlock -d "$cryptroot" -n drive; then
            cryptsetup luksOpen "$cryptroot" drive
          fi
        '';
      }
    );
  in
  finalConfiguration.foo
#+END_SRC

The above expression is tangled to [[config-5-tpm.nix][config-5-tpm.nix]].
